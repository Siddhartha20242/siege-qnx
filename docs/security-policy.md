# QNX security policy as a hardening profile

The other profiles (`prio`, `isolate`, `budget`) change how the CPU is shared.
This one changes **who is allowed to do what**. Siege compiles a QNX security
policy, pushes it into the running kernel, and gives the detector and the
attackers different security types. Then the same attacks are replayed.

```sh
./siege show secpol        # the results below, in your terminal, nothing installed
./siege list --config examples/secpol/siege.json
```

## What is used

| Piece | Where |
|---|---|
| Policy source, one file per variant | [`image/secpol/*.secpol`](../image/secpol/), generated by [`tools/gen_secpol.py`](../tools/gen_secpol.py) |
| Compiled on the host with `secpolcompile -m` (mutable policy, so it can be pushed after boot) | [`scripts/build.sh`](../scripts/build.sh) |
| Loaded in the target with `secpolpush`, types assigned with `on -T` | [`image/pipeline.sh`](../image/pipeline.sh) |
| Attacker starts at priority 9 and tries to raise itself; a refusal is counted and printed | [`pipeline/attacker.c`](../pipeline/attacker.c) (`ATK ... prio_denied=`) |
| 12 scenarios, 5 profiles, 10 runs each, **expected outcome written before any run** | [`examples/secpol/siege.json`](../examples/secpol/siege.json) |
| Raw results | [`examples/secpol/results/`](../examples/secpol/results/) |

Two types matter. `det_t` is the detector and its supervisor. `atk_t` is the untrusted
neighbour. Everything else keeps the default type with all abilities, as before any policy.

| Profile | What `atk_t` is denied |
|---|---|
| `secpol-connect` | connecting to the detector's channel, so it cannot send to it at all |
| `secpol-ceiling` | any priority above **9** (the pipeline runs at 10). In the policy this is the line `priority:1-9` in the attacker type's ability list, in place of the plain `priority` ability. `secpolcompile` accepted it and the attacker's attempts to raise itself were refused (`prio_denied` in its output). QNX's [security policy language](https://qnx.com/developers/docs/8.0/com.qnx.doc.security.system/topic/manual/secpol_language.html) documents a range for an ability, and the `secpol` utility page shows `priority:255` in an example, so the form is consistent with the documented syntax; we have not read the page that defines the priority ability's exact meaning, so check it before copying the line |
| `secpol-names` | the `pathspace` ability and `allow_attach`, so it cannot register a service name |
| `secpol` | all three |
| `secpol-least` | all three, and the detector's type keeps only 5 abilities (see below) |
| `secpol-minimal` | all three, and the detector's type holds no abilities |

## Results

Failed runs out of 10 (5-second runs, 20 ms deadline, QEMU, QNX 8.0 aarch64le):

| Scenario | none | connect | ceiling | names | all three |
|---|---|---|---|---|---|
| baseline, no attacker | 0 | 0 | 0 | 0 | 1 |
| CPU hog at priority 20 | **10** | **10** | 0 | **10** | 1 |
| `workflood` at priority 30 | **10** | 0 | 0 | **10** | 0 |
| AI neighbour at priority 20 | **10** | **10** | 0 | **10** | 0 |
| memory bandwidth at priority 10 | **10** | 5 | 0 | **10** | 1 |
| name squat after a restart | **10** | **10** | **9** | 0 | 0 |
| same, with the supervisor's owner check | 0 | 0 | 1 | 0 | 0 |
| plain mutex priority inversion | **10** | **10** | **10** | **10** | **10** |

(The full 12-row table is `./siege show secpol`. Cells with a few failures and no clear
cause are flaky; read them as "sometimes", not as a rate.)

What this shows, in order of how much it matters:

1. **The three mechanisms are different, and each fixes only its own class.** Denying
   the connection stops `workflood` (the attacker never sends a request) and does
   nothing for a CPU hog. The priority ceiling stops every attack that depends on
   outranking the pipeline, and does nothing for the name squat. Denying name
   registration stops the squat and nothing else. Combined, they cover all of those.
2. **No policy fixes the plain mutex.** A lock held by a low-priority process is not
   something a permission can express. It fails everywhere, as predicted.
3. **A ceiling of 10 does not work.** An attacker allowed up to the pipeline's own
   priority is at equal priority, which already breaks the pipeline (see the CPU hog at the
   same priority in the main results). The ceiling has to be strictly below
   the pipeline: 9. This is a configuration mistake the measurement caught, and it is
   exactly the kind a reader copying a policy could make.
4. **The policy can break the defender's own defence.** The first run of the owner-check
   scenario failed 10 of 10 under `connect` and 9 of 10 under `ceiling`, against a
   prediction of "pass". The supervisor checks who owns the service name by connecting to
   whatever holds it, and the policy gave `det_t` no right to connect to `atk_t`. Adding
   `allow det_t atk_t:channel connect` fixed it (0 and 1 failures of 10 on the re-run). The
   earlier results are kept in
   [`examples/secpol/results-before-fix/`](../examples/secpol/results-before-fix/).

## Least privilege: what the detector actually needs

In the policies above the detector's type holds every ability, as the pipeline did before any
policy. That is the opposite of least privilege, so we measured what it needs
([`tools/minimize_policy.py`](../tools/minimize_policy.py), raw data in
[`docs/results/secpol-minimize.json`](results/secpol-minimize.json)).

1. 63 probe policies were built into one image, each removing **one** ability from the
   detector's type.
2. Each was loaded on the target and the pipeline run twice with the detector killed and
   restarted by its supervisor two seconds in (that exercises starting, naming,
   scheduling and restarting a process).
3. An ability counts as not needed only if every trial passed.

**58 of 63 passed in every trial.** Five (`runstate`, `umask`, `trace`, `chroot`,
`xprocess_mem_read`) passed only 1 of 2. They have no plausible connection to this
pipeline, and the baseline itself fails now and then in QEMU, so we treat them as noise,
but we kept them in `secpol-least` to be safe.

**A zero-ability type passing is a finding about the pipeline, not a validation of the probes.** A detector type with *no* abilities at
all (`bare`, an extra control variant) also passed the supervised-kill run 6 of 6. That means this pipeline, on the paths we ran, does not
use any ability the policy gates. It cannot tell us the probes can detect a missing ability, so a **positive control** was run separately:
asking for priority 100 (above the unprivileged limit) works in a process of the open-policy type and is refused with
"Operation not permitted" in a process of the zero-ability detector type. So the type really is enforced, and the pipeline simply did not
need what it lacks. The policy statements it does need are the channel rules and `allow_attach`.

**Removing `priority` does not cap priority; granting it with a range does.** Under the zero-ability types the supervisor still ran at
priority 50 (`pidin` showed `50r`), because ordinary processes may use priorities up to 63 without the ability. The ceiling works only
because the attacker type is granted `priority:1-9` explicitly: its attempts to raise itself to 30 were refused (`prio_denied`). Anyone
copying the policy needs to know which of the two they are relying on.

Then the whole matrix was run under `secpol-least` and `secpol-minimal` (all three
restrictions, with the detector holding 5 and 0 abilities). Failures out of 10:

| Scenario | all three, full abilities | least (5) | minimal (0) |
|---|---|---|---|
| baseline, no attacker | 1 | 1 | 0 |
| CPU hog at priority 20 | 1 | 0 | 1 |
| `workflood` at priority 30 | 0 | 1 | 0 |
| AI neighbour at priority 20 | 0 | 2 | 0 |
| memory bandwidth at priority 10 | 1 | 0 | 0 |
| name squat after a restart | 0 | 0 | 0 |
| same, owner check | 0 | 0 | 0 |
| plain mutex priority inversion | **10** | **10** | **10** |

Taking the detector's abilities from 63 to 0 changed nothing we can see beyond the
run-to-run noise. `least` shows 2 of 10 on the AI neighbour, the largest scatter in these
cells; we did not investigate whether it is noise or a real effect of the five kept abilities.

**Limits.** Only the detector's type was reduced; the camera, controller and shell are
still `default` with every ability. "Not needed" means not needed by the paths we
exercised (start, name, serve, restart, be killed): it says nothing about code paths we
didn't run, or other QNX versions. Removing one ability at a time can miss two that are
needed together, which is why the combined policies were run, not assumed.

## Re-running the cells that missed

The cells that missed their predictions were re-run at larger sizes, to see whether they were noise
([`examples/secpol/repeats/`](../examples/secpol/repeats/)):

| Cell | First run | Larger re-run |
|---|---|---|
| baseline, no attacker, `none` | 0/10 | **1/30** (95% interval 1 to 17%) |
| baseline, `secpol` | 1/10 | **1/30** |
| baseline, `secpol-least` | 1/10 | **1/30** |
| CPU hog at 20, `secpol` | 1/10 | **0/20** (0 to 16%) |
| CPU hog at 20, `secpol-minimal` | 1/10 | **1/20** |
| AI neighbour at 20, `secpol-least` | 2/10 | **0/20** |

A clean run with no attacker fails about 1 time in 30 in this emulator, with or without a policy, so a single failed run in ten is
inside the noise. The AI-neighbour cell that looked like the largest effect did not repeat. The other missed cells
(`workflood` under `least`, name squat with the detector alive under `none`, the owner check under `ceiling`) were not re-run at
this size.

## Predictions versus outcome

The expected pass or fail for 63 scenario-and-profile pairs was written into
`examples/secpol/siege.json` before each profile was run (the `least` and `minimal`
expectations were set equal to those of the all-three policy, before their runs). A "pass"
means zero failures in 10.

**55 of 63 matched.** The eight misses are each one or two failed runs out of ten, in cells
predicted to have none:

| Cell | Failures |
|---|---|
| baseline, all three | 1/10 |
| baseline, `least` | 1/10 |
| CPU hog at 20, all three | 1/10 |
| CPU hog at 20, `minimal` | 1/10 |
| `workflood`, `least` | 1/10 |
| AI neighbour, `least` | **2/10** |
| name squat with the detector alive, no policy | 1/10 |
| owner check, `ceiling` | 1/10 |

Two of these are runs with **no attacker at all** (baseline). Single bad runs happen in QEMU without any
attack, so one failure in ten is not evidence that a policy leaks. It does mean we cannot
claim these cells are perfect, and we do not.

## What this does not show

* **This is a launch-time configuration test, not an isolation test.** The attacker is put in `atk_t` by the launcher, and the policy is loaded at run time with `secpolpush` from a shell of type `default`, which holds every ability (including the ones to load a policy and to change a process's type). Anything running as `default` could replace the policy. A deployment would load an immutable policy at boot, which we did not do; the `-m` (mutable) compile option exists only so a test can push several policies.

* **Two scenarios were pinned afterwards.** `cpu hog @prio 10` and `memory bandwidth @prio 10` had
  no prediction written before their runs; their expected outcomes in `examples/secpol/siege.json` were
  set from the results so that CI covers every case. They are not part of the 55-of-63 count.

* **Two code versions.** The first five profiles were measured before the robustness fixes in
  [`code-review.md`](code-review.md); `least` and `minimal` after. The spot check there found no
  changed outcome, but the policy matrix itself was not re-run on the fixed code.

* **QEMU only.** Timing is emulated. The policy mechanisms are the real QNX ones, but no
  hardware run has been done.
* **The attacker's type is assigned by the launcher** (`on -T atk_t`). That models a deployment
  where the untrusted software is started with a restricted type. It does not model an
  exploit in a running process, and Siege does not use secure boot or the policy
  generation tools.
* **The camera, controller and shell keep every ability.** The detector's type was
  measured down to almost nothing (above); the rest of the pipeline was not.
* **A policy cannot stop an authorised client misbehaving.** If a neighbour is allowed to
  talk to a shared service and runs at the pipeline's priority, no permission is
  violated and the pipeline still suffers. That is the case the scheduling profiles
  exist for.
* **Evidence, not certification.** Passing runs show these attacks were stopped in these
  runs, not that the system is free of interference.
